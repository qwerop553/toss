# 모의투자 사이트 설계

작성일: 2026-09-06
상태: 승인됨, 미착수

## 목적

한국 주식 모의투자 웹사이트. 실제 시세로 가상 매매를 하고 손익을 추적한다.
연습 목적의 개인 프로젝트이며, 코드는 프로젝트 소유자가 직접 작성한다.

## 확정된 전제

| 항목 | 결정 |
|---|---|
| 시세 소스 | 토스증권 오픈 API (실시간 조회) |
| 대상 시장 | 한국 주식 (KOSPI/KOSDAQ) |
| 체결 방식 | 시장가 즉시체결만 (최우선 호가 기준) |
| 사용자 | 다중 사용자 + 이메일/비밀번호 회원가입 |
| 화면 | Thymeleaf 서버 렌더링 |

지정가 대기주문, 호가창 매칭, 실시간 푸시, 랭킹, 차트는 범위 밖이다.
필요해지면 그때 별도로 설계한다.

## API 확인 결과 (2026-09-06)

- **인증** — Bearer 토큰. `expires_in` 86400초(24시간).
- **호가 조회** — 응답에 체결가/현재가 필드가 없고 `asks`/`bids` 호가창만 온다.
  가격과 수량은 문자열로 온다. 통화는 KRW.
- **호출 제한** — 초당 최대 15회.

### 남은 확인 사항

1. 토큰 재발급 호출 자체에 제한이 있는가 (있으면 토큰 캐싱이 필수가 된다)
2. 별도의 현재가/체결가 조회 엔드포인트가 있는가
3. 다종목 배치 조회 엔드포인트가 있는가 (포트폴리오 화면의 N회 호출을 1회로 줄인다)

## JSON 파싱

Spring Boot 4.1은 **Jackson 3**(`tools.jackson.*`)을 쓴다.
Jackson 2의 `com.fasterxml.jackson.*`와 패키지가 다르므로,
2.x 기준 예제를 그대로 가져오면 import가 맞지 않는다.

호가 응답에서 실제로 쓰는 값은 최우선 매도호가와 최우선 매수호가 둘뿐이므로
DTO 클래스를 만들지 않고 `readTree`로 트리를 탐색해 꺼낸다.
DTO 매핑은 클래스 세 개와 `jackson-module-kotlin` 의존성을 요구하는데
값 두 개에는 과하다. 쓰는 필드가 늘어나면 그때 전환한다.

주의: `path()`는 없는 키에 예외 대신 빈 노드를 반환하고,
빈 노드의 `asLong()`은 0이다. 필드명을 잘못 쓰면 에러 없이 0원 호가가 나온다.
아래 "빈 호가" 검사가 이 오타까지 함께 막는다.

## 기술 스택

기존 스타터에서 추가할 의존성:

- `spring-boot-starter-web`
- `spring-boot-starter-thymeleaf`
- `spring-boot-starter-data-jpa`
- `spring-boot-starter-security`
- `spring-boot-starter-validation`
- H2 (파일 모드). 필요해지면 Postgres로 교체.

HTTP 호출은 Spring 내장 `RestClient`를 쓴다. 별도 HTTP 라이브러리를 추가하지 않는다.

## 도메인 모델

엔티티는 넷. 그 이상 만들지 않는다.

- **User** — 이메일, 비밀번호 해시
- **Account** — User와 1:1, `cashBalance`
- **Holding** — Account, 종목코드, 수량(`quantity`), 총매입금액(`totalCost`)
- **Trade** — 체결 기록. 종목코드, BUY/SELL, 수량, 체결가, 체결시각

### Order 엔티티를 만들지 않는 이유

시장가 즉시체결에서는 주문 시점과 체결 시점이 같다.
`Trade` 하나가 주문과 체결을 모두 표현한다.
지정가 대기주문을 도입하는 시점에 `Order`가 필요해진다.

## 시세와 체결가 규칙

호가 응답에는 단일 "현재가"가 없다. 최우선 호가로 체결한다.

- **매수** → 최우선 매도호가(asks 중 최저가)로 체결
- **매도** → 최우선 매수호가(bids 중 최고가)로 체결
- **평가금액** → 최우선 매수호가 기준. 실제로 청산 가능한 가격이라 보수적이고,
  매도 체결가와 기준이 일치한다.

하나의 가격으로 양방향을 체결시키면 사자마자 팔아도 본전이 되어
모의투자로서 틀린 신호를 준다. 최우선 호가를 쓰면 스프레드가 자연히 반영된다.

### 배열 순서에 의존하지 않는다

확인된 응답에서 `asks`는 내림차순이었다. 즉 `asks[0]`은 최우선 매도호가가 아니라
가장 비싼 호가다. 순서를 가정하지 말고 `asks`의 최솟값, `bids`의 최댓값을 계산한다.
한 줄이면 되고, API가 순서를 바꿔도 깨지지 않는다.

### 호가 잔량은 무시한다

주문 수량이 최우선 호가 잔량을 넘어도 전량을 최우선 호가로 체결한다.
실제로는 다음 호가까지 소진되지만 학습 목적에는 과하다.
한계를 알고 넘기는 선택이며, 필요해지면 호가를 순회하며 가중평균 체결가를 계산한다.

## 핵심 설계 원칙

매수와 매도는 단일 진입점을 통과한다:

```
TradeService.execute(userId, code, side, qty)
```

이 메서드 하나가 하나의 `@Transactional` 안에서 다음을 수행한다:

1. 시세 조회
2. 검증 (매수는 현금 잔고, 매도는 보유 수량)
3. 잔고와 보유 종목 갱신
4. Trade 저장

검증을 컨트롤러에 두지 않는다. 매수/매도/추가될 화면마다 규칙이 복제되면
언젠가 한 군데가 어긋난다.

## 작업 순서

각 단계는 브라우저나 테스트로 동작을 확인한 뒤 다음으로 넘어간다.

1. **시세 조회** — 종목코드를 넣으면 현재가가 표시되는 페이지
2. **인증** — 회원가입/로그인. 가입 시 Account 생성 및 초기 현금 지급
3. **매수** — 현금 차감, Holding 생성 또는 증분
4. **매도** — 보유 수량 검증, `totalCost`를 수량 비율만큼 차감
5. **포트폴리오** — 보유 종목 목록에 현재가를 붙여 평가금액과 수익률 표시

1번이 먼저인 이유: 토스 API가 예상과 다르면 나머지 설계가 통째로 흔들린다.
가장 불확실한 것을 먼저 확인한다.

## 알려진 함정

### 금액은 전부 Long (원 단위 정수)

한국 주식은 가격이 항상 정수 원이다. 호가 단위가 정해져 있어 소수점 가격이 없으므로
체결금액, 잔고, 손익이 모두 정수로 닫힌다. `Long`이면 정확하고 비교도 단순하다.

`BigDecimal`은 소수가 있을 때 값을 하는데 여기엔 소수가 없다. 과하다.
미국 주식이나 암호화폐(소수점 수량·가격)로 확장할 때 다시 검토한다.

`Double`은 어느 경우에도 쓰지 않는다.

### 평균단가를 저장하지 않는다

평균단가는 나눗셈이라 정수로 떨어지지 않는다. 저장하면 매수할 때마다
반올림한 값을 다시 반올림하게 되어 오차가 누적된다.

`Holding`에는 `totalCost`와 `quantity`만 저장하고, 평균단가는 화면에 표시할 때만
나눈다. 저장값이 전부 정수로 유지되고, 손익도 `평가금액 - totalCost`로 정수끼리 끝난다.

### 시세 조회는 캐시한다

포트폴리오에 10종목이 있으면 화면 한 번 여는 데 10회 호출이 발생한다.
`@Cacheable`에 TTL 5초를 건다. 종목당 초당 0.2회로 15회 한도에 여유가 크다.

한도가 넉넉해 보여도 캐시는 필요하다. 다중 사용자이므로
인기 종목 하나에 사용자가 몰리면 한도에 닿는다.

### 토큰은 캐싱한다

24시간 만료이므로 요청마다 재발급할 이유가 없다.
메모리에 보관하고 만료 전에 갱신한다.

### 시세 조회 실패 시 주문을 거부한다

시세를 가져오지 못하면 체결하지 않고 실패로 끝낸다.
마지막 캐시 값으로 체결시키면 틀린 가격에 잔고가 움직인다.
