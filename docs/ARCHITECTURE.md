# 설계 문서

이 프로젝트가 **왜 이렇게 생겼는지**를 적는다. 무엇을 하는지는 [README](../README.md),
파이썬 쪽 세부 규칙은 [research/CLAUDE.md](../research/CLAUDE.md)에 있다.

여기서 다루는 것: 두 프로세스로 나눈 이유, 그 둘이 주고받는 계약, 그리고
"이건 이렇게 하면 안 된다"의 근거. 코드를 고치기 전에 읽으면 같은 함정을 두 번
파지 않는다.

---

## 1. 전체 그림

```
                         토스증권 OpenAPI
                    ┌──────────┴──────────┐
            WebSocket│                     │REST
         (계정당 2개 제한)                  │
                     ▼                     ▼
        ┌────────────────────────┐   ┌──────────────────┐
        │  server  (Kotlin)      │   │ research (Python)│
        │  :8080                 │   │                  │
        │                        │   │ data/candles.py  │
        │  TossFeedClient        │   │  과거 캔들 백필    │
        │   ├ 호가 ─┐            │   │        │         │
        │   └ 체결 ─┤            │   │        ▼         │
        │           ▼            │   │  market_data.db  │
        │      PriceSocketHandler│   │        │         │
        │           │  /ws       │   │        ▼         │
        │           ├────────────┼──▶│ backtest/   전략 검증
        │           │            │   │ paper/app.py 모의투자
        │           │            │   │        │         │
        │           │            │   │ signal_runner.py │
        │           │            │◀──┤  전략 실시간 실행  │
        │  SignalController      │   └──────────────────┘
        │   POST /api/signals    │
        │           │            │
        │           ▼            │
        │      브라우저 배너       │
        └────────────────────────┘
```

두 프로세스는 **같은 것의 두 언어 버전이 아니다.** 역할이 다르다.

| | server (Kotlin/Spring) | research (Python) |
|---|---|---|
| 책임 | 연결 유지 · 상태 보관 · 전달 · 검증 | 전략 계산 · 검증 · 데이터 수집 |
| 성공 기준 | **안 죽는 것** | **정답을 내는 것** |
| 이유 | JVM은 롱러닝 데몬에 강하다 | pandas/numpy, 반복이 빠르다 |
| 실패해도 | 러너가 죽어도 호가 화면은 산다 | 서버가 죽어도 러너는 재연결한다 |

### 왜 굳이 둘인가

리서치를 파이썬으로 하고 실행을 JVM에 두는 건 실제 트레이딩 회사의 표준 분업이다.
근거는 두 가지다.

**반복 속도와 안정성은 다른 축이다.** 전략 탐색은 하루에 수십 번 고쳐 돌린다 —
여기서는 pandas의 표현력이 전부다. 반면 장중 8시간 동안 소켓을 붙들고 있는 코드는
고칠 일이 거의 없고 대신 안 죽어야 한다. 한 언어로 둘 다 하면 둘 중 하나가 손해를 본다.

**옮기면 잃기만 한다.** 전략 56개와 `indicators.py` 370줄이 이미 파이썬에 있다.
백테스트는 pandas가 압도적이고, 지표 계산을 JVM으로 옮긴다고 빨라지지도 않는다
(어차피 I/O 바운드다). 반대로 재연결·백오프·스레드 안전성을 파이썬으로 옮기면
JVM이 공짜로 주던 것을 직접 만들어야 한다.

## 2. 왜 파이썬이 토스에 직접 붙지 않는가

**토스 업스트림 웹소켓은 계정당 2개다.** 이 한 줄이 구조를 결정했다.

처음 설계는 양쪽이 각자 토스에 붙는 것이었다. 그러면 server 1개 + 러너 1개로
한도를 다 써서 모의투자 웹앱(`paper/app.py`)을 띄울 자리가 없다. 셋 다 쓰려면
누군가는 양보해야 하는데, 시세를 이미 물고 있는 쪽이 나눠주는 게 자연스럽다.

그래서 **토스에 붙는 것은 server 하나**로 두고, 파이썬은 server의 `/ws`를 구독한다.

```
  [A안 — 폐기]                      [B안 — 현재]

  토스 ──┬── server                 토스 ─── server ──┬── 브라우저
         └── 러너                                     └── 러너
  업스트림 2개 (한도 소진)            업스트림 1개 (여유 1개)
```

부수 효과가 둘 있다.

**좋은 쪽**: 러너는 실시간 경로에 토스 토큰이 아예 필요 없다. 시크릿이 한 프로세스에만
있으면 된다. (과거 캔들 백필에는 여전히 필요하다 — 그건 REST라 연결 수와 무관하다.)

**대가**: `PriceSocketHandler`가 두 스레드에서 불리게 됐다. 호가·체결은 피드 스레드,
시그널은 HTTP 워커 스레드다. `WebSocketSession.sendMessage`는 스레드 세이프가 아니라서
동시에 쓰면 `IllegalStateException`이 난다. 그런데 전송 실패를 "죽은 세션"으로 보고
목록에서 빼는 처리와 겹치면 **멀쩡한 구독자가 조용히 퇴장당한다** — 브라우저는
새로고침 전까지 화면이 멈춘 것처럼 보인다. 스프링의 `ConcurrentWebSocketSessionDecorator`로
감싸 전송을 직렬화했고, 같이 딸려오는 시간·버퍼 상한이 느린 구독자가 시세 스레드를
붙잡는 것도 막는다. A안이었으면 피드 스레드 하나뿐이라 안 겪었을 문제다.

## 3. 프로세스 간 계약

두 프로세스를 묶는 것은 **URL 두 개와 JSON 필드 이름**이 전부다. 서로의 내부 구조를
모른다. 이 절만 지키면 양쪽을 독립적으로 고칠 수 있다.

### 3.1 server → 구독자 (`ws://localhost:8080/ws`)

한 소켓에 여러 종류가 흐른다. 수신 측은 `type`으로 분기하고,
**모르는 `type`은 조용히 무시한다** — 나중에 종류가 늘어도 안 깨지게 하기 위한 규칙이다.

```jsonc
// 호가
{"type": "orderbook", "symbol": "005930", "asks": [...], "bids": [...]}

// 체결
{"type": "trade", "stockCode": "005930", "price": 71500, "volume": 10,
 "timestamp": "2026-09-11T17:16:33.504+09:00"}

// 시그널
{"type": "signal", "id": 1, "stockCode": "005930", "side": "BUY", "price": 71500,
 "strategy": "EmaCrossStrategy", "timestamp": "2026-09-11T13:45:00+09:00",
 "note": "ema9 > ema21"}
```

- `price`·`volume`은 **숫자**다. 토스 원문은 문자열로 오는데 파싱 경계에서 한 번만
  Long으로 바꾼다. 안 바꾸면 쓰는 쪽이 전부 문자열 비교를 하게 되고 `"9" > "10"`이
  참이 되는 식으로 조용히 틀린다.
- **`timestamp`와 `note`는 없으면 키 자체가 빠진다.** `null`로 보내지 않는다.
  받는 쪽이 `"없음"`과 `null`을 구분하느라 분기를 늘리지 않게 하기 위해서다.
- 호가만 `symbol`이고 나머지는 `stockCode`다. **의도된 불일치**다 — 호가의 `symbol`은
  이미 브라우저와 기존 화면이 쓰고 있어서 이름을 바꾸면 돌아가는 소비자를 깨뜨린다.
  새로 생긴 메시지만 나머지 코드베이스가 쓰는 이름으로 통일했다.

### 3.2 러너 → server (`POST http://localhost:8080/api/signals`)

```json
{
  "stockCode": "005930",
  "side": "BUY",
  "price": 71500,
  "strategy": "EmaCrossStrategy",
  "timestamp": "2026-09-11T13:45:00+09:00",
  "note": "선택 — 없으면 키 생략"
}
```

| 필드 | 규칙 |
|---|---|
| `stockCode` | 6자리 숫자 |
| `side` | `BUY` 또는 `SELL` |
| `price` | 정수, 0 초과 |
| `strategy` | 전략 클래스 이름 |
| `timestamp` | ISO-8601, **오프셋 포함** |
| `note` | 선택. 없으면 키 생략 |

응답: `200 {"received": true, "id": 1}` / `400 {"error": "사유"}`

**양쪽이 같은 검증을 중복으로 한다.** 러너의 `build_payload()`도 6자리·BUY/SELL·
`price>0`을 확인하고 server의 `SignalController`도 확인한다. 중복이 아니라 의도다 —
보내는 쪽에서 터뜨리면 스택 트레이스가 남아 원인을 알 수 있지만, 서버가 400만
돌려주면 로그를 봐도 왜 신호가 안 들어갔는지 알기 어렵다.

**의미론 주의**: `timestamp`는 *신호가 난 봉의 시작 시각*이고 `price`는 *그 봉의 종가*다.
발송 시각도, 다음 봉에서 실제로 체결 가능한 가격도 아니다. 백테스트와 대조하려면
봉 기준이어야 하기 때문이다.

### 3.3 장애 시 동작

| 상황 | 동작 |
|---|---|
| server가 안 떠 있음 | 러너는 죽지 않는다. 지수 백오프로 재연결 |
| server 재시작 | 러너가 알아서 다시 붙는다 |
| POST 실패(거부/타임아웃/400) | 로그만 남기고 계속. 봉 처리는 멈추지 않는다 |
| 러너가 죽음 | server는 무관. 호가 화면은 그대로 |
| 토스 업스트림 끊김 | server가 지수 백오프 재연결(최대 30초) + PING 60초 |
| 전략이 예외를 던짐 | 그 봉만 버리고 계속 |

러너가 자기가 보낸 시그널을 `/ws`로 되돌아 받는데, "모르는 type 무시" 규칙에
자연히 걸려서 무시된다.

## 4. 데이터 흐름 세 갈래

### 4.1 실시간 시세 (WebSocket)

```
토스 ──▶ TossFeedClient ──▶ parseEvent ──┬──▶ OrderbookStore  (최신 호가 보관)
                                          ├──▶ TradeService    (모의 체결 판정)
                                          └──▶ PriceSocketHandler ──▶ /ws 구독자
```

`parseEvent`는 **절대 예외를 던지지 않는다.** 깨졌거나 일부만 온 프레임은 버린다.
여기서 예외가 나면 웹소켓 읽기 루프 밖으로 새어나가 연결이 끊기고, 재접속할 때마다
같은 자리에서 또 죽어 피드가 영영 살아나지 않는다. 프레임 하나 버리는 쪽이 훨씬 싸다.
파이썬 쪽 `parse_trade`도 같은 규율을 지킨다.

### 4.2 시그널 (WebSocket 구독 + HTTP)

```
/ws ──▶ parse_trade ──▶ [정규장 필터] ──▶ MinuteBars ──봉이 닫힘──▶ 전략 실행
                                                                      │
                        server ◀── POST /api/signals ◀── build_payload ┘
```

**봉은 타이머가 아니라 "다음 분의 첫 틱"으로 닫는다.** 타이머를 쓰면 거래 없는 분에
빈 봉이 생겨 전략 입력에 없던 봉이 끼고, 이벤트 루프에 태스크가 하나 더 붙는다.
대가는 그날 마지막 봉이 안 닫힌다는 것이다.

**매 봉마다 프레임을 통째로 다시 만들고 전략도 처음부터 돌린다.** 증분 계산을 하지
않는 이유는 두 가지다. 지표가 ewm/rolling이라 앞 구간이 바뀌면 뒤가 바뀌고, 무엇보다
**백테스트와 같은 코드로 같은 숫자**가 나와야 한다. 1분에 한 번 수천 행짜리 pandas
연산은 공짜에 가깝다.

**중복 신호를 막는 상태를 따로 들고 있지 않다.** 전략의 `generate_signals()`가 프레임
전체를 보고 `to_signals`의 상태머신을 처음부터 다시 돌리므로, 마지막 봉의 값이 곧
"이번 봉에서 일어난 사건"이다. 봉 하나를 정확히 한 번씩만 평가하니 같은 신호가 두 번
나가지 않는다.

### 4.3 과거 캔들 (REST)

```
토스 REST /api/v1/candles ──▶ data/candles.py ──▶ market_data.db (SQLite)
                                                        │
                                     ┌──────────────────┴──────────────┐
                                     ▼                                 ▼
                              backtest/ (검증)            signal_runner 워밍업
```

`INSERT OR IGNORE` 증분이라 재실행이 안전하다. **429가 자주 난다** — 실측으로 50종목 중
17종목이 rate limit으로 실패했고 재시도 로직이 없다. 증분이니 실패한 것만 다시 돌리면 된다.

**워밍업이 왜 필요한가:** 전략의 EMA/rolling은 초기값이 시드에 끌려다닌다. 장 시작
직후 받은 틱 몇 개만으로 지표를 계산하면 "신호가 안 나는" 게 아니라 **틀린 지표값으로
난 신호**가 나온다. 과거 봉을 앞에 붙이면 첫 실시간 봉부터 백테스트와 같은 지표값
위에서 판단한다.

## 5. 상태 저장소

| | 위치 | 내용 | 비고 |
|---|---|---|---|
| `market_data.db` | 저장소 루트 | 캔들 (`candles` 테이블) | SQLite. gitignore. **현재 없음 — 아래 참고** |
| `research/results.db` | research | 백테스트 결과 캐시 (`daily` 83,496행, 250MB) | SQLite. gitignore |
| `research/paper.db` | research | 파이썬 모의투자 `fills` | SQLite. gitignore |
| `server/data/paper.mv.db` | server | Kotlin 모의투자 | H2. gitignore |

**모의투자 상태는 `fills`에서 파생한다.** 현금·보유수량·평균단가를 따로 저장하지
않는다. 두 곳을 맞추다 어긋나면 잔고가 조용히 틀린다.

**H2 경로가 상대경로다** (`jdbc:h2:file:./data/paper`). 실행 위치에 따라 DB가 갈린다 —
gradle로 띄우면 `server/data/`에 생긴다. 알려진 거슬림이고 아직 안 고쳤다.

### 캔들 데이터가 지금 없다

`market_data.db`는 2026-09-11 작업 중 소실됐고 백업이 없다. 백테스트나 러너 워밍업을
돌리기 전에 다시 받아야 한다.

```bash
cd research
python -m data.candles --kospi50 --interval 1d    # 먼저. 몇 분
python -m data.candles --kospi50 --interval 1m    # 1시간 이상, 429로 일부 실패
```

**없는 채로 돌려도 터지지 않는다는 게 함정이다.** 백테스트는 빈 프레임을 받고,
러너는 "워밍업 0봉" 경고를 찍은 뒤 시드에 끌려다니는 지표값으로 신호를 낸다.
조용히 틀린 결과가 나오는 종류의 실패다.

데이터를 커밋하지 않는 정책이라 저장소가 백업 역할을 못 한다. 오래 모은 수집물이
생기면 저장소 밖에 사본을 두는 편이 낫다 — 1분봉은 429 때문에 한 번에 다 못 받는다.

## 6. 넘지 않는 선

### 실매매 코드를 넣지 않는다

**토스에는 모의투자 sandbox가 없다.** 서버가 실서버 하나뿐이라 주문 API를 부르면
실제 돈이 나간다. 그래서 `paper/toss.py`는 읽기 전용 함수만 노출한다.

이 경계를 지키는 점검은 문자열 검색이 아니라 **구조 검사**다: `paper/`에 GET 외의
HTTP 메서드가 없는지, 요청 헬퍼에 주문·계좌 경로가 인자로 넘어가는 자리가 없는지를 본다.
예전에는 위험한 엔드포인트의 문자열 자체를 금지했는데, 그러면 "이걸 부르지 마라"는
경고문이 그 문자열을 담을 수 없어 경고가 무력해졌다 — **위험한 것의 이름을 부르지
못하는 경고는 경고가 아니다.**

### 정규장(09:00~15:30) 밖에서는 동작하지 않는다

`paper/broker.py`는 시간외 주문을 거부하고, `signal_runner.py`는 시간외 체결을 분봉에
넣지 않는다. 시간외단일가는 10분 단위 단일가라 체결이 뜨문뜨문 찍히고 그 사이 봉은
거래량이 0이거나 비어 있다. 전략은 정규장 분봉으로 백테스트한 것이므로,
**그런 봉 위에서 난 신호는 한 번도 검증된 적 없는 입력에 대한 출력**이다.

막는 자리를 '신호 전송'이 아니라 **'틱 투입'**으로 잡았다. 시간외 체결이 일단 봉에
들어가면 그 봉의 고가·저가·거래량이 이미 오염되고, 그 봉은 다음 정규장까지 프레임에
남아 워밍업 구간의 지표값을 끌고 다닌다. 신호만 막으면 오늘 신호는 안 나가지만
내일 신호가 틀린 지표 위에서 나온다.

09:00~15:30을 하드코딩하지 않고 장 구간 API를 쓴다. 휴장일과 조기폐장이 있어서
시간만 비교하면 공휴일 내내 "장중"이 된다. 다만 그 호출은 네트워크를 타므로
**날짜가 바뀔 때만 조회해 캐시한다.**

### 시세 루프에서 네트워크를 타지 않는다

`tz_now()`의 이전 버전은 여기서 장 캘린더 API를 불렀다. 이 함수가 체결 프린트마다
(이벤트 루프 위에서) 불리다 보니 API 호출 한 번만 실패해도 예외가 웹소켓 루프를 뚫고
나가 연결이 끊기고, 재접속마다 같은 자리에서 또 죽어 피드가 영영 안 살아나는
무한루프가 됐다. 지금은 로컬 타임존 오프셋만 돌려준다.

`MarketHours`가 조회를 캐시하는 것도 같은 이유다.

### 브라우저는 토스 웹소켓에 직접 못 붙는다

핸드셰이크에 `Authorization` 헤더가 필요한데 브라우저 WebSocket API는 커스텀 헤더를
못 넣고, 넣을 수 있어도 토큰이 프론트로 샌다. 그래서 백엔드가 업스트림을 물고 팬아웃한다.

## 7. 실패를 다루는 방식

이 프로젝트에서 가장 위험한 건 **조용한 실패**다. 돈이 걸린 코드에서 "아무 일도
일어나지 않음"과 "고장남"이 구분되지 않으면 고장을 며칠 뒤에 발견한다.

| 자리 | 처리 | 이유 |
|---|---|---|
| 업스트림 끊김 | 화면 상단 빨간 배너 | 조용히 두면 체결됐어야 할 지정가가 왜 안 됐는지 모른다 |
| 워밍업 부족 | WARNING 로그 | "신호가 안 나는" 상태가 정상처럼 보인다 |
| 장 구간 조회 실패 | 닫힌 것으로 보되(fail closed) 로그 | 모르는 채 신호를 내는 것보다 안 내는 게 안전하다 |
| 시간외 체결 버림 | 구간 전환 시 한 번만 로그 | 매 틱마다 찍으면 수십 건이 쏟아져 로그가 무의미해진다 |
| 전략 예외 | 그 봉만 버리고 계속 | 전략 하나가 터져서 시세 연결이 끊기면 안 된다 |

**fail closed의 대가를 인정한다.** 장 구간을 못 알아내면 그날은 신호가 안 나간다.
이건 의도지만, 조용히 그러면 안 되므로 억제할 때마다 로그를 남긴다.

## 8. 알려진 한계

- **큐 포지션을 모델링하지 않는다.** 지정가가 실제보다 잘 체결된다.
- **그날 마지막 봉이 닫히지 않는다.** 타이머 없이 다음 틱으로 닫는 설계의 대가다.
- **호가 이력이 없다.** `orderbook:kr`을 실시간으로 받지만 흘려보내고 버린다.
  `market_data.db`에는 `candles` 테이블 하나뿐이다. 미시구조 전략을 제대로 하려면
  그 스트림을 적재하는 것이 첫 단계이고, 그 전까지 `strategies/microstructure/`는
  봉 모양으로 근사한 대용치일 뿐이다.
- **수집 재시도가 없다.** 429가 나면 그 종목은 그냥 실패한다.
- **`signal_runner`가 `paper/toss.py`에 의존한다.** 정규장 필터가 `get_session()`을
  재사용하면서 생겼다. 장 구간은 모의투자 로직이 아니라 시장 메타데이터이므로
  원래는 `data/`에 있는 게 맞다.
- **모의투자가 둘이다.** Kotlin `trade/`(262줄)와 파이썬 `paper/`(1,680줄)가 겹친다.
  파이썬 쪽이 훨씬 정교하고(부분체결·시장가 다단 스윕·수수료 반올림), Kotlin 쪽은
  Spring 연습 결과물이다. 합칠지는 아직 결정하지 않았다.

## 9. 다음에 손댄다면

우선순위대로 적는다. 근거는 "지금 무엇이 가장 틀리기 쉬운가"다.

1. **호가 이력 적재.** 직접 쌓은 호가·체결 데이터는 남이 못 구한다. 미시구조 전략의
   전제 조건이기도 하다.
2. **`get_session`을 `data/`로 이사.** 러너와 `paper/`의 결합을 끊는다.
3. **H2 경로 고정.** 실행 위치에 따라 잔고가 갈리는 걸 없앤다.
4. **수집 재시도.** 429에 백오프를 넣으면 `--kospi50` 한 번으로 끝난다.
5. **신호 → 자동주문.** 여기로 가면 `TradeService`의 리스크 검증을 반드시 태워야 한다.
   러너가 이상한 신호를 뱉어도 **서버가 막는** 구조가 게이트웨이를 두는 진짜 이유다.
